# Playbook · 复盘自己项目

> **开工前**:先按 SKILL.md「开工前询问」问清用户水平 + 是否方便给项目文件,校准讲解方式后再开始 9 维诊断。

用户给一个已有 benchmark 项目（文件或描述），按下列 9 维检查清单逐维度诊断，产出按严重度排序的问题清单 / 复盘报告。
引导规则:
1. **先读项目实际** - 要求用户给项目文件或描述;Read 其数据集/评分脚本/Rubric/配置,逐条对照检查清单指出**该项目的具体问题**(如"你的 judge prompt 没有长度惩罚 -> 长度偏差风险"),而非通用建议。用户没给时先问"方便给我项目文件吗?",再基于描述作答并标注"未读实际材料"。
2. **结合具体代码、讲透结构** - 每条诊断必须指向用户项目里的具体文件:行号(如 `cases/.../tests/kpis.json:65`),不停留在"你的 kpis.json"这种泛指。并先给一段"项目结构↔代码对应"导览(目录树 + 关键文件职责);**熟练档可跳过导览,但仍须落到具体文件/行号**。
3. 先问清评估对象与目标,再逐维度检查;每条问题给:问题描述 + 风险 + 改进建议 + 来源(源 ID + 小节)。
4. **先解释后下结论** - 新手/中级档:术语先一句白话(查 `references/glossary.md`);熟练档可紧凑。
5. 关键论断标原则编号,可对照 `references/design-principles.md` 与 `references/knowledge-map.md`。
6. **讲清运行时流程** - 用 1-2 个真实 case 串起运行时:先跑哪个文件、进哪个容器/环境、每步输入输出是什么,便于定位问题出在哪一环。

> 每个维度格式：**查**（检查什么）-> **红旗**（常见反模式）-> **依据**（原则编号 + 源 ID / 小节）。R2、R9 的依据为知识图谱小节或多源小节，未单列原则编号处注明来源。

## 检查清单（逐维度）

### R1. 评估对象是否解耦

- **查:**是否说清测的是模型 / agent / harness？是否做了模型替换实验（model swap）来区分瓶颈来源？
- **红旗:**把 agent 表现直接归因于模型能力；未区分模型能力不足与 harness 设计缺陷就下"换模型"的结论。
- **依据:**原则 1（chapter6 §引言；yehudai-survey §7 Discussion > Decoupling LLM & Harness Evaluation）。

### R2. 能力维度覆盖

- **查:**维度是否覆盖目标能力？有无遗漏（尤其安全 / 鲁棒性 / 边界案例）？维度过窄还是过宽？
- **红旗:**维度过窄无法收敛或过宽无法诊断；漏掉安全 / 鲁棒性；只选自己擅长的维度造成选择性报告。
- **依据:**knowledge-map §B（chang-survey §3 WHAT TO EVALUATE；yehudai-survey §2 Agent Capabilities Evaluation 四核心能力；guidebook §Benchmarks to know in 2025 通用维度）。

### R3. 数据集五挑战

- **查:**明确 vs 开放？真实 vs 可控？多样 vs 系统？成本 vs 覆盖？防泄漏？逐项核对。
- **红旗:**任务描述歧义不可复现；无防泄漏手段（公开数据易进训练集）；验证依赖主观判断而非可执行标准；规模贪大忽略信噪比。
- **依据:**原则 2-6（chapter6 §任务数据集设计的核心挑战；原则 6 防泄漏另见 guidebook §MANAGING CONTAMINATION）。

### R4. 指标误用

- **查:**Pass@k / Pass^k / Best@k 是否用对？测稳定性（Pass^k）还是能力上限（Pass@k）？有无安全零容忍否决项？过程指标与结果指标是否双重覆盖？
- **红旗:**回归测试用 Pass@k 掩盖不稳定性；探索性评估用 Pass^k 因偶发波动误报；漏安全否决项；只看结果漏轨迹指标。
- **依据:**原则 11、12（chapter6 §评估指标体系，结果与质量指标含 Pass@k / Pass^k / Best@k；guidebook §SAMPLING 采样指标 pass@k / maj@n / cot@n / avg@n）。

### R5. Rubric 与评分

- **查:**Rubric 是否符合四准则（专家指导 / 全面覆盖含陷阱 / 标准权重与一票否决 / 自包含可验证）？否决项是否设定？judge 是否校准？是否防同源偏见？
- **红旗:**Rubric 抽象不可验证（违反原则 9 自包含可验证）；无否决项；同源 judge 不防偏见（原则 10）；未校准就放量 LLM judge。
- **依据:**原则 9、10（chapter6 §LLM-as-a-Judge：自动化评估的核心 > Rubric 四准则 + 同源模型问题与多源异构评判；guidebook §With judge models / §PROS AND CONS OF USING JUDGE-LLMS / §EVALUATING YOUR EVALUATOR）。

### R6. 统计显著性

- **查:**样本量是否够分辨目标改进？分差是否超过噪声带宽？是否报告置信区间 / 配对分析（McNemar）？多重比较是否收紧或复跑？
- **红旗:**小样本下结论；几十个用例就分辨 2-3% 改进；未做配对分析把抽样噪声当改进信号；多重比较不校正。
- **依据:**原则 13（chapter6 §评估结果的统计显著性；guidebook §Statistical validity，含配对分析 McNemar、多重比较收紧）。

### R7. 可复现性

- **查:**prompt / 模板 / 归一化 / 种子 / 模型加载是否固定且透明？指标定义是否清晰同名同实现？
- **红旗:**指标同名不同实现；归一化缺失；prompt 与 few-shot 不固定；复现细节不透明无法横向比较。
- **依据:**原则 14（guidebook §So, you can't reproduce reported model scores?，含 Different code base / Subtle implementation or loading difference / Different prompt / Different normalization）。

### R8. 成本与效率

- **查:**是否报告 token / 时间 / 成本？轮次与上下文是否控制？多轮上下文成本是否非线性增长？有无预算上限？
- **红旗:**成本非线性增长未控；无预算上限；只选便宜模型而非控轮次 / 稳前缀 / 压缩历史。
- **依据:**原则 15（chapter6 §Agent 系统的成本分析，成本构成要素 / 成本优化策略 / 成本监控与预算控制）。

### R9. 质量迭代

- **查:**有无渐进式 gating（5 -> 50 -> 全量）？有无金标集校准 judge？人工抽检比例多少？评估集是否静态不迭代？有无观察 -> 假设 -> 实验 -> 验证闭环？
- **红旗:**未校准就放量；金标集不覆盖边界案例；评估集静态饱和无回归机制；gating 阈值过松导致低质数据混入。
- **依据:**原则 16（chapter6 §从 Benchmark 报告到系统改进 > §持续迭代）；chapter12 §12.2.6 扩展与优化建议（渐进式评估 gating：5->50->全量、accuracy>0.8 才放量）+ §12.4 数据生成质量评估（数据生成质量验证流程）；chapter6 §数据质量控制与迭代改进。
