# Playbook · 构建 benchmark

> **开工前**:先按 SKILL.md「开工前询问」问清用户水平 + 要测什么/现有 setup,校准讲解方式后再开始 Step 1。

本模式用头脑风暴式引导，把"造一个 benchmark"拆成 10 个依次确认的决策。
引导规则:
1. **结合用户实际** - 问清要测什么模型/agent、现有 setup(必要时 Read 用户给的代码/数据/配置),据此给具体方案,而非通用清单。
2. 一次问一个(或一小簇)问题、多选优先、关键论断标来源、可按需引用原文。
3. **先解释后下结论** - 新手/中级档:每个概念先一句白话(查 `references/glossary.md`)再问;熟练档可紧凑。
受众推断已在启动时完成,沿用其结论调整术语深度;若在 Step 1 发现偏差,就地修正。

> 每步格式：**问什么**（给可选答案，多选优先）→ **依据**（原则编号 + 源 ID/小节，可对照 `references/design-principles.md` 与 `references/knowledge-map.md`）→ **陷阱**（常见反模式）。Step 1 为需求澄清，无外部依据；Step 10 为产出汇总，无陷阱。

---

## Step 1. 目标与受众

- **问什么:**测 LLM 还是 agent？为谁做（自用 / 研究组 / 社区发布）？发布还是内部用？
- **依据:**无（需求澄清）。受众沿用启动推断；若发现偏差在此修正。
- **陷阱:**未先界定评估对象就选指标；把"我想发 paper"和"我要选模型"混为一谈，导致后续指标采样错位。

## Step 2. 评估对象界定

- **问什么:**你要测的是模型能力、agent 整体，还是 harness？打算用模型替换实验（model swap）区分瓶颈来源吗？
- **依据:**原则 1（chapter6 §引言；yehudai-survey §7 Discussion > Decoupling LLM & Harness Evaluation）。
- **陷阱:**把 agent 表现直接归因于模型，忽略 harness；不做 model swap 就下"换模型"的结论。

## Step 3. 能力维度

- **问什么:**从 taxonomy 中勾选要测的维度（多选：推理 / 工具调用 / 规划 / 自我反思 / 记忆 / 事实性 / 鲁棒性 / 安全伦理 / …）。
- **依据:**knowledge-map §B（chang-survey §3 WHAT TO EVALUATE；yehudai-survey §2 Agent Capabilities Evaluation 四核心能力；guidebook §Benchmarks to know in 2025 通用维度）。
- **陷阱:**维度过宽无法收敛；漏掉安全 / 鲁棒性；只选自己擅长的维度造成选择性报告。

## Step 4. 数据集设计

- **问什么:**任务描述如何平衡明确与开放？难度如何分层？如何防泄漏？如何保证可验证？
- **依据:**原则 2-8（chapter6 §任务数据集设计的核心挑战 / §任务描述的精确性设计 / §任务复杂度的层次化设计 / §可验证性与客观性保障 / §任务分布的系统性设计；原则 6 防泄漏见 chapter6 §数据泄漏防范 + guidebook §MANAGING CONTAMINATION）。
- **陷阱:**忽略防泄漏（公开数据易进训练集）；验证依赖主观判断而非可执行标准；单一难度无法定位能力短板。

## Step 5. 评估环境

- **问什么:**工具调用型还是人机交互型？静态还是动态？需不需要沙盒 / 用户模拟？
- **依据:**knowledge-map §C（chapter6 §自动评估环境；yehudai-survey §5 Core Benchmark Dimensions > Environment + §6 Frameworks for Agent Evaluation > Gym-like Environments）。
- **陷阱:**人机交互任务一开始就暴露全部信息（违反渐进式透露）；动态环境不做状态隔离导致用例间污染。

## Step 6. 指标体系

- **问什么:**用哪些过程指标 / 结果指标？要测稳定性（Pass^k）还是能力上限（Pass@k）？有无安全否决项？
- **依据:**原则 11、12（chapter6 §评估指标体系，结果与质量指标含 Pass@k / Pass^k / Best@k；guidebook §SAMPLING 采样指标 pass@k / maj@n / cot@n / avg@n；安全合规见 chapter6 §评估指标体系 安全与合规指标）。
- **陷阱:**Pass@k 与 Pass^k 混用（回归测试用 Pass@k 掩盖不稳定性）；漏安全零容忍项；只看结果漏轨迹指标。

## Step 7. 评分方法

- **问什么:**有标准答案可自动匹配（EM / BLEU / functional scorer）？还是需 LLM-as-judge / Rubric？还是配对比较（Elo / Bradley-Terry）？
- **依据:**knowledge-map §F（guidebook §METRICS / §FUNCTIONAL SCORERS / §With judge models；chapter6 §LLM-as-a-Judge：自动化评估的核心 > Rubric 四准则 + 同源模型问题与多源异构评判；chapter6 §配对比较与模型排名）。Rubric 设计遵循原则 9，judge 偏见遵循原则 10。
- **陷阱:**Rubric 抽象不可验证（违反原则 9 自包含可验证）；同源 judge 不防偏见（原则 10）；未校准就放量 LLM judge。

## Step 8. 统计与成本

- **问什么:**评估集多大？分差要超噪声带宽多少才信？成本预算多少？多轮上下文成本如何估算？
- **依据:**原则 13（chapter6 §评估结果的统计显著性；guidebook §Statistical validity，含配对分析 McNemar、多重比较收紧）；原则 15（chapter6 §Agent 系统的成本分析，成本非线性增长与优化策略）。
- **陷阱:**几十个用例就分辨 2-3% 改进（落噪声带宽内）；忽略成本非线性增长；不做配对分析把抽样噪声当改进信号。

## Step 9. 质量控制

- **问什么:**是否小样本 gating（5 → 50 → 全量）？有无金标集校准 judge？人工抽检比例多少？
- **依据:**原则 16（chapter6 §从 Benchmark 报告到系统改进 > §持续迭代）；chapter12 §12.2.6 扩展与优化建议（渐进式评估 gating：5→50→全量、accuracy>0.8 才放量）+ §12.4 数据生成质量评估（数据生成质量验证流程）；chapter6 §数据质量控制与迭代改进（人工抽检 / 评判者校准）。
- **陷阱:**未校准就放量 LLM judge；金标集不覆盖边界案例；gating 阈值过松导致低质数据混入。

## Step 10. 产出

- **产出**：《评估方案文档》，含：评估对象、能力维度、数据集规范（任务模板 / 难度 / 防泄漏 / 验证）、环境、指标、评分方法（Rubric 模板）、统计与成本、质量控制。
- 生成后提示用户：可进入"复盘模式"对既有 benchmark 做对照检查，或进入"梳理模式"把方案落到 benchmarks.md。
